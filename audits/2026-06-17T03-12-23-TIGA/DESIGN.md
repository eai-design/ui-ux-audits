## Design QA Requirements

### High-Fidelity Requirements

- Before view must be grounded in the exported HTML snapshot and screenshots.
- After view must preserve the product's existing visual language and only change what is necessary.
- No clipped text, broken icons, oversized icons, overlapping labels, squeezed typography, incomplete data, or rough red-circle annotations.
- Annotation layer should be toggleable if annotations are used.
- Any full After HTML must be complete usable HTML/CSS/JS and must pass visual self-check against the original screenshot.

### Icon Requirements

- Prefer existing SVG/use/class icons from the icon inventory.
- If replacing icons, provide complete inline SVG or exact existing symbol/class reference.
- Specify size, container, color token, hover/focus/disabled state, aria-label, and tooltip.
- Toolbar/navigation icons should usually stay within observed 14-24px geometry unless the source UI intentionally uses another size.
- Empty-state illustrations may be larger only when intentionally present in the original UI.
- If the original icon is semantically wrong, replacement is allowed but must include source, semantic reason, size, stroke/fill, and implementation.
- The Icon Board must show all likely usable captured icons and at least 30 items when enough icons exist.
- Each icon must include an actual call method: inline SVG snippet, use href, class name, image src, or selector/component reference.

### UX Guidance Requirements

- Every primary action must explain the next step.
- Every async action should show loading, success, error, and recovery states.
- Empty states should tell users what to do next.
- Export/download actions should explain output format.

## Rules: Do

- Use the exported HTML snapshot as the Before source of truth.
- Use screenshots as visual truth for proportions, density, and placement.
- Use semantic design tokens for proposed changes, but preserve observed tokens first.
- Preserve the product's existing visual language unless a redesign is explicitly requested.
- Provide selector/module-level implementation guidance.
- Provide complete usable icons through inline SVG, existing symbol/use references, image sources, or available icon classes.
- Define keyboard, pointer, and touch behavior for interactive components.
- Include accessibility pass/fail checks.
- Phrase optional refinements as 建議, not mandatory defects.

## Rules: Don't

- Do not create a generic UI unrelated to the captured product.
- Do not replace polished original components with a different style just because it looks preferable.
- Do not allow clipped text, overlapping labels, broken icons, or hidden focus indicators.
- Do not allow oversized icons, squeezed text, incomplete visible data, distorted buttons, or unexpected scrollbars.
- Do not use placeholder icons, emoji substitutes, or vague icon labels.
- Do not introduce one-off spacing or typography exceptions without justification.
- Do not use ambiguous labels or non-descriptive actions.
- Do not treat captured viewport size as a fixed resolution requirement.

## Guideline Authoring Workflow

1. Restate the design intent in one sentence.
2. Identify the target page/module and user task.
3. Use the HTML snapshot to define the Before baseline.
4. Use UX JSON to identify behavior issues.
5. Use screenshots to verify visual proportions, data completeness, and component geometry.
6. Use design tokens and icon inventory to define implementation-ready minimal changes.
7. Produce Design QA findings first; generate full After pages only when explicitly requested.
8. End with accessibility checks, anti-patterns, and QA checklist.

## Required Output Structure

- Context and goals
- Before baseline from HTML snapshot
- UX behavior findings from JSON
- Design tokens and foundations
- Component-level rules and states
- Icon replacement and accessibility table
- Design QA visual checklist with local Before/After component previews when needed
- Selector-level implementation diff
- Accessibility requirements and testable acceptance criteria
- Anti-patterns and prohibited implementations
- QA checklist

- [ ] Identify the primary user task on this page.

- [ ] Convert ambiguous states into visible status chips.
- [ ] Ensure empty states tell users what to do next.

## Quality Gates

- Every non-negotiable rule must use "must".
- Every recommendation should use "should".
- Every accessibility rule must be testable in implementation.
- Every icon recommendation must include implementation source and accessibility label.
- Every After proposal must map back to the captured HTML snapshot or target module.
- Teams should prefer system consistency over local visual exceptions.
- Every optional visual refinement must be marked as 建議.
- Every full After HTML must preserve original tokens unless the change is justified.
